# IPv6 profile comparison, confirmed bypasses and proposed changes

Updated 2026-11-24. Baseline: **Mimo 2.1 build 8**, pinned **Mihomo v1.19.34**. The profile changes and a standalone engine patch for true ping dropping are now implemented in a [standalone Global, zero-rule test profile](../Profiles/mimo-global-ipv6-test.yaml) and tested in `mimo-vm`. The managed app's generated profiles, lifecycle and released binaries remain unchanged. The table's managed-app proposal and the requested standalone Global test have different rule policies, described below.

Two paths bypassed the engine in controlled VM tests: ICMPv6 echo forwarding and NAT64 IPv6 TCP/UDP outside the default TUN routes. A separate, conditional UDP fallback was reproduced with Mimo-shaped rules and an HTTP proxy. The `mp-sg-global.example.yaml` sample can be an effective IPv4 workaround for ordinary hostname traffic using its DNS and selected proxy, while still permitting native IPv6 bypass. Tests using its IPv6 switches confirmed direct ping and TCP packets; the sample's NAT64-specific case remains inferred rather than separately packet-tested.

The proposed Tailscale integration follows the sample's simple method: **static address exclusions and native Quad100 DNS**. It has no dynamic Tailscale `utunN` binding, `TS-NATIVE`/`TS-DIRECT` proxy provider, provider file, provider port or port fallback. Mimo still owns its own TUN for protected traffic.

## The two confirmed bypass mechanisms

### 1. ICMPv6 is forwarded outside ordinary proxy rules

Both current Mimo and the Clash Verge file enable gVisor TUN and omit `disable-icmp-forwarding`:

```yaml
ipv6: true
tun:
  enable: true
  stack: gvisor
  auto-route: true
```

In the pinned engine, ICMP takes a separate `PrepareConnection` path. Without the disable flag, it calls direct ping forwarding using native socket controls rather than the TCP/UDP rule matcher. The observed log was:

```text
[ICMP] ... --> [2606:4700:4700::1111]:0 using DIRECT
```

Thus an ordinary rule such as `IP-CIDR6,::/0,REJECT,no-resolve` cannot stop this path. Actual engine Global mode also does not force ICMP through the selected SOCKS5 proxy. The profile's `strict-route: false` is not the switch that selects this ICMP behavior.

The initial, now-superseded mitigation was:

```yaml
tun:
  disable-icmp-forwarding: true
```

With it, three echo requests still entered TUN but none left `en0`; the log changed to `using fake ping echo`. Ping reported success because the engine synthesized replies locally. This meets the narrow requirement to stop native ICMP egress, but **does not provide real ping through the proxy or prove remote reachability**. Ordinary SOCKS5 provides TCP and UDP operations, not raw ICMP forwarding. If real proxied ping is required, a compatible tunnel/transport and engine implementation must be evaluated separately. The user subsequently rejected synthetic replies. The current test revision therefore drops echo packets inside the gVisor ICMP handler, before both forwarding and local-reply paths (including the handler’s own-address shortcut). Other ICMP types retain normal handling. This needs the engine/dependency patches; it cannot be obtained from that flag alone. Native LAN and Tailnet pings are preserved by their native routes, not manufactured by the proxy.

Sources: [pinned ICMP handler](https://github.com/MetaCubeX/mihomo/blob/v1.19.34/listener/sing_tun/prepare.go), [SOCKS5 protocol](https://www.rfc-editor.org/rfc/rfc1928).

### 2. NAT64 addresses miss the default Darwin TUN routes

The relevant configuration is `auto-route: true` without explicit IPv6 `route-address` entries. In the pinned macOS route builder, the default ranges are:

```text
100::/8, 200::/7, 400::/6, 800::/5,
1000::/4, 2000::/3, 4000::/2, 8000::/1
```

Their union omits `::/8`. Both `64:ff9b::/96` and `64:ff9b:1::/48` are inside the omitted range. Checking a route under `2001:db8::/32` therefore cannot establish NAT64 coverage.

The baseline route lookup for `64:ff9b::101:101` selected `en0`, while `2606:4700:4700::1111` selected the test TUN. Three TCP packets and three UDP packets to the NAT64 address appeared on `en0`, with none entering TUN. No NAT64 translator or successful connection was established by this experiment; the evidence is the unproxied packet path.

The broader candidate replaces the incomplete IPv6 auto-ranges with:

```yaml
tun:
  route-address:
    - "::/1"
    - "8000::/1"
```

These two prefixes cover the IPv6 space before exclusions. The engine splits explicit `route-address` entries by address family; these IPv6 entries do not themselves replace IPv4 defaults. If a profile already has explicit IPv4 entries, preserve them. Our VM tests narrowed IPv4 capture to the test range so the SSH management connection remained native.

With the candidate, both tested public IPv6 and NAT64 destinations used TUN, and no destination packets appeared on `en0`. A route-only check also placed `64:ff9b:1::1` in TUN. The Mimo-shaped candidate's reject rule stopped TCP/UDP; the Clash Global candidate selected the proxy. These routes do not override every more-specific OS route or interface-bound socket. Native Tailnet and loopback exceptions remain intentional.

Source: [pinned sing-tun v0.4.29 route builder](https://github.com/MetaCubeX/sing-tun/blob/v0.4.29/tun_rules.go#L145). The project's pinned engine declares that dependency in [go.mod](https://github.com/MetaCubeX/mihomo/blob/v1.19.34/go.mod).

## Sample assessment: effective IPv4 workaround, with remaining IPv6 leaks

**Does it leak?** Its IPv6 strategy permits native IPv6 traffic to bypass the proxy. In the controlled test using the same IPv6 switches, three echo requests and five TCP packets left the VM directly. This confirms the bypass mechanism, not every path in a complete live sample deployment.

**Is it effective despite that?** It can be effective for normal hostname-based connections that use the sample's DNS and selected proxy: avoiding local IPv6 connections removes one opportunity for an application to choose native IPv6. This is useful behavior even though it does not contain traffic that still uses IPv6. Its practical effectiveness depends on resolver use, available addresses and the actual Global proxy selection; we did not measure a success percentage or reproduce the user's unidentified service.

The sample uses:

```yaml
ipv6: false
dns:
  ipv6: false
proxies:
  - name: MP-SG
    # Other existing proxy fields are omitted here.
    ip-version: ipv4
```

For a typical connection that uses this resolver, the intended sequence is:

1. `dns.ipv6: false` suppresses the AAAA response, so this DNS path does not give the application an IPv6 destination. A query for A can still receive the sample's IPv4 fake-IP.
2. The application connects to that IPv4 address. IPv4 TUN capture delivers it to the engine, which recovers the hostname and uses the selected Global proxy.
3. The sample's proxy server is an IPv4 literal, and `ip-version: ipv4` constrains applicable local proxy resolution. The local proxy connection therefore does not depend on a native IPv6 destination route.

This sequence requires the actual `GLOBAL` selection to be `MP-SG` or a group leading to it. Defining a group named `Proxy` does not by itself establish that selection. It also requires the relevant DNS request to use the sample's resolver; independent DoH, caches or literal addresses are outside that assumption.

The tradeoff is that top-level `ipv6: false` also prevents TUN IPv6 capture in this engine. None of these settings disables native macOS IPv6. A literal IPv6 destination, cached address, independent resolver or application-provided address can still use the native route. In those cases, the sample supplies neither proxy handling nor a packet-level IPv6 block. An IPv6-only hostname can instead become unavailable through the suppressed-AAAA path; availability and absence of direct egress are different outcomes.

The controlled sample-switch test recorded three native echo requests and five native TCP packets, with no corresponding IPv6 packets entering TUN. It used literal addresses and disabled DNS to isolate capture behavior. It therefore demonstrates the residual bypass, not a failure of AAAA suppression to reduce ordinary DNS-driven IPv6 use.

For **NAT64 specifically**, suppressing AAAA can keep clients on the IPv4/proxy path instead of supplying a synthesized IPv6 address. However, if an application obtains a NAT64 address elsewhere or already has one, the sample's disabled IPv6 capture cannot intercept it. Given a usable native route, direct egress is expected from the configuration and engine code. No separate sample NAT64 packet test or successful NAT64-translated connection was performed. The precise conclusion is **useful avoidance for some clients, with an uncontained NAT64 path when avoidance does not apply**, rather than either universal safety or a claim that every sample connection leaks.

The user's service improvement is consistent with this IPv4 workaround being useful, but could also involve DNS, proxy choice or another difference. We cannot assign a cause without the service details. Its improvement and the demonstrated residual bypass can both be true.

The `ip-version` on a SOCKS5 entry concerns applicable local resolution, including its server and locally resolved UDP destinations. It does not force every TCP hostname sent to the remote SOCKS5 server to resolve to IPv4. IPv6 used by the remote proxy is also distinct from a local direct bypass.

## Separate conditional finding: UDP can fall through to DIRECT

This finding does not change the two principal bypass categories above. It is an additional failure path when the selected adapter lacks UDP support.

The current active rule list ends with `MATCH,Proxy`. In engine Rule mode, the matcher skips a matching adapter that does not support UDP. If no later rule matches, its default is DIRECT. Mimo supports HTTP proxies, which do not acquire UDP support merely because the generated YAML includes `udp: true`.

The test used an IPv4 fake-IP for a synthetic hostname with only an AAAA record. When TUN restored the hostname, the destination IP was initially unknown. The first `IP-CIDR6,::/0,REJECT,no-resolve` rule therefore did not match. The HTTP proxy was skipped, DIRECT was selected, internal DNS obtained the IPv6 address, and three UDP packets left natively. Client-facing `dns.ipv6: false` did not prevent this internal resolution.

```text
[UDP] ... --> ipv6-path-proof.invalid:443 doesn't match any rule using DIRECT
```

The tested fix is a terminal rejection after the desired proxy rule:

```yaml
rules:
  # Existing managed and mode-specific rules precede these entries.
  - MATCH,Proxy
  - MATCH,REJECT
```

The candidate logged `match Match using REJECT`, made no synthetic upstream DNS query for that flow and emitted no native IPv6 UDP packets. This is not evidence that the current SOCKS5 proxy with working UDP support takes the same fallback path. It is also not a rule fix for actual engine Global mode, which bypasses ordinary matching.

Source: [pinned rule matcher](https://github.com/MetaCubeX/mihomo/blob/v1.19.34/tunnel/tunnel.go#L654), [fake-IP preprocessing](https://github.com/MetaCubeX/mihomo/blob/v1.19.34/tunnel/tunnel.go#L289), [HTTP adapter](https://github.com/MetaCubeX/mihomo/blob/v1.19.34/adapter/outbound/http.go).

An intentional domain-based DIRECT rule presents a related late-resolution concern: it can choose a direct adapter before IPv6 is known. The final reject rule does not undo an earlier intentional DIRECT match. A static IPv4-only direct adapter for ordinary website bypasses is a proposed separate safeguard; it still needs targeted runtime tests. Native Tailnet exclusions remain a separate policy.

## Proposed profile changes

These are excerpts to merge into generated profiles, not a complete profile to install. Proxy credentials, listeners and existing mode-specific rules are omitted. No source/profile changes have been made by this investigation.

### IPv6 capture and direct ICMP suppression

```yaml
ipv6: true

tun:
  enable: true
  stack: gvisor
  auto-route: true
  auto-detect-interface: true
  strict-route: false
  # inet6-address is omitted: use the engine's default IPv6 TUN address.
  disable-icmp-forwarding: true
  route-address:
    - "::/1"
    - "8000::/1"
  route-exclude-address:
    - "100.64.0.0/10"
    - "fd7a:115c:a1e0::/48"
```

The proposal uses the **default engine IPv6 TUN address**, with no `inet6-address` override. In pinned v1.19.34 that default is currently `fdfe:dcba:9876::1/126`, the same numeric address that Mimo presently sets explicitly. The change is to let the engine supply it, not to change IPv6 route coverage. The explicit `route-address` prefixes remain necessary to close the default route gap. Source: [pinned engine defaults](https://github.com/MetaCubeX/mihomo/blob/v1.19.34/config/config.go#L552).

The IPv6 route pair and static exclusions were tested together. The Clash candidate already omitted `inet6-address` and used the engine default; the Mimo-shaped candidate set the same address explicitly. Public/NAT64 test routes entered Mimo's test TUN, the Tailnet IPv6 route stayed on the native Tailscale tunnel, and `::1` stayed on `lo0`. No dynamic Tailscale interface name appears in this configuration. Real peer connectivity was not tested in that run.

### Simple native Tailscale and MagicDNS

Follow the sample's native resolver method:

```yaml
dns:
  ipv6: false
  nameserver-policy:
    "+.ts.net":
      - "100.100.100.100"
  nameserver:
    - "https://1.1.1.1/dns-query#Proxy"
  proxy-server-nameserver:
    - "https://1.1.1.1/dns-query"
```

Retain fake-IP exclusions for native Tailnet names, including `+.ts.net`, so applications receive native addresses. Retain the macOS resolver/search-domain integration needed by system clients. The proposal replaces interface-bound `TS-NATIVE` and `TS-DIRECT` with native routing; no provider file is prepared, polled or refreshed when the Tailscale interface number changes. Native Quad100 DNS and any engine-handled Tailnet IPv4/domain exceptions use ordinary direct routing. Tailscale owns the actual routes and connectivity.

The static native DNS method now passes the connected full-name MagicDNS and native-route checks in the standalone VM profile. It is not yet a qualified installed-app replacement. Verify system resolver integration, that disconnects do not send private names to a public fallback, and recovery across native interface changes. Keep failures explicit. Custom Tailscale split-DNS domains beyond `.ts.net` require separate policy work and tests; this excerpt does not claim to support them automatically.

Provider-specific rewrites and profile reloads disappear from the proposed Tailnet interface-change path. Existing general network-change verification remains a separate core/supervisor policy. Removing the dynamic provider does not automatically authorize removing all network-change checks.

### Managed rejection and final fallback

Keep Mimo's engine `mode: rule` in both protected UI modes. Preserve the first ordinary rule:

```yaml
rules:
  - IP-CIDR6,::/0,REJECT,no-resolve
  # Native Tailnet IPv4/domain exceptions, LAN rules and Rule-only
  # website bypass blocks remain between the first and final rules.
  - MATCH,Proxy
  - MATCH,REJECT
```

Native Tailnet IPv6 excluded at the OS routing layer does not reach this blanket IPv6 rule. Explicit IPv6 requests sent into Mimo's proxy listener still encounter it. This distinction must be documented as an intentional native Tailnet exception, not advertised as a guarantee that all IPv6 traffic is blocked.

### Ownership and lifecycle

The eventual implementation remains owned by core/supervisor. GUIs request shared changes and display their results. Keep the existing closed-transition barrier, startup/recovery checks, generation fencing and full cleanup of legacy PF/DNS/IPv6 resources. Do not add a permanent active IPv6 firewall or modify macOS IPv6 service preferences for this proposal.

In Direct, remove Mimo's TUN and owned resolver as today. Stop/uninstall must also remove obsolete provider files/resources from older installations and retain the existing legacy firewall cleanup. No proposed profile excerpt changes the released app's current workflow by itself.
